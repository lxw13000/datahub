# Elasticsearch S3 快照备份恢复操作手册

适用环境：

- 测试 ES：`elasticsearch8-test`，Elasticsearch `8.19.16`，宿主机 HTTP 端口 `9211`。
- 正式 ES：`elasticsearch8`，Elasticsearch `8.19.16`，按正式 Compose 实际映射端口执行。
- 运行环境：AWS EC2 上的 Docker 单节点 Elasticsearch。

本文先在测试环境完成一次“创建仓库 -> 创建快照 -> 恢复为新索引 -> 校验 -> 删除演练数据”的闭环，再将同样流程迁移到正式环境。

## 0. 先理解：Kibana、Elasticsearch 与 S3 各自做什么

之前如果是在 Kibana 的 **Snapshot and Restore** 页面操作，本质上也是 Kibana 调用 Elasticsearch 的 Snapshot API。Kibana 只是管理页面，不会把备份文件下载到浏览器、Kibana 容器或本机磁盘。

改用 AWS S3 后，实际链路是：

```text
你（curl 或 Kibana 页面）
        |
        | 创建快照 / 恢复快照 API
        v
Elasticsearch 容器
        |
        | EC2 IAM Role 身份 + HTTPS 443
        v
AWS S3 Bucket
        |
        +-- 保存 Elasticsearch Snapshot 文件
```

因此，S3 是快照文件的真正存放位置；Kibana 可有可无。当前测试 Compose 没有部署 Kibana，所以本文用 `curl` 命令操作。如果后续部署 Kibana，可在 **Dev Tools** 中执行相同 API：把文档中的 `curl ... -X PUT/POST` 外壳去掉，仅粘贴 `PUT _snapshot/...` 或 `POST _snapshot/...` 与 JSON 请求体即可。

### 0.1 这套快照会备份什么

| 内容 | 是否由 ES Snapshot 备份 | 当前建议 |
| --- | --- | --- |
| `sano_wallet_*` 等业务索引数据、Mapping、Settings、Alias | 是 | 备份，本文的 `sano_*` 已覆盖 |
| `sano_import_task` 任务索引 | 是 | 名称符合 `sano_*`，会一并备份 |
| 指定索引的文档数据 | 是 | 可按单索引或 `sano_*` 选择 |
| 集群全局状态、模板、Pipeline、ILM | 可选 | 当前默认 `include_global_state: false`，避免恢复时覆盖目标环境配置 |
| Kibana 保存的对象 | 仅快照包含相应 `.kibana*` 系统索引时 | 当前未部署 Kibana，无需处理；以后单独决定是否备份 |
| Docker Compose、`elasticsearch.yml`、Nginx、es-server 的 YAML | 否 | 继续由 Git、服务器配置备份或 IaC 管理 |
| Docker 镜像、es-server Jar | 否 | 由 Docker Hub 镜像标签和项目源码管理 |
| Elasticsearch `data` 目录 | 不能直接复制作为备份 | 只能通过 Snapshot API 备份到 S3 |

一句话概括：**S3 Snapshot 备的是 ES 中可查询的数据与索引结构，不是整台服务器或 Docker 服务的完整镜像。**

### 0.2 你实际需要做的事情

不需要把 S3 挂载到 Docker，也不需要在 ES 容器内手工上传文件。只需：

1. 在 AWS 创建私有 S3 Bucket。
2. 给运行 ES 的 EC2 绑定允许访问该 Bucket 的 IAM Role。
3. 通过一次 `PUT _snapshot/...` 把该 Bucket 注册为 ES 的“快照仓库”。
4. 以后创建快照时，ES 自动将数据上传到 S3；恢复时，ES 自动从 S3 下载。

## 1. 原则与边界

1. 使用 Elasticsearch Snapshot/Restore API 备份，**不要**复制或压缩 `data` 目录。文件级复制不具备 Elasticsearch 所需的一致性，不能作为可恢复备份。
2. 一个 S3 仓库只能有一个 Elasticsearch 集群进行写入。测试和正式环境应使用不同的 S3 Bucket；若确有需要共享 Bucket，必须使用不同 `base_path`，且恢复方以 `readonly: true` 注册。
3. S3 仓库内的对象只能由 Elasticsearch Snapshot API 创建、删除和清理。不要手工删除对象、配置对象过期规则，也不要将对象迁移到 Glacier / Deep Archive。
4. 快照是在线操作，无需停止 ES；它以分片为单位保存某一时间范围内的数据视图，并非全局精确瞬时点。
5. 快照可跨集群恢复，但目标 ES 版本不得低于快照来源版本，索引兼容性也必须满足 Elasticsearch 要求。测试、正式均为 `8.19.16` 时可直接互相演练。

官方参考：

- [Snapshot and restore](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/snapshot-restore.html)
- [S3 repository](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/repository-s3.html)
- [Restore a snapshot](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/snapshots-restore-snapshot.html)

## 2. 建议的 S3 规划

测试与正式各使用一个独立 Bucket，避免测试误写、误删正式快照：

| 环境 | 示例 Bucket | 示例 Repository | `base_path` |
| --- | --- | --- | --- |
| 测试 | `sano-es-test-snapshots-账号-区域` | `sano_s3_test` | `elasticsearch8-test` |
| 正式 | `sano-es-prod-snapshots-账号-区域` | `sano_s3_prod` | `elasticsearch8-prod` |

Bucket 名称必须在 AWS 全局唯一。文中的名称均为示例，执行前替换成实际名称。

建议的 Bucket 设置：

1. 创建在 EC2 所在 AWS Region，例如 `ap-southeast-1`，避免跨区域传输成本和延迟。
2. 开启 **Block Public Access**，保持 Bucket 私有。
3. 开启默认服务端加密：测试可用 SSE-S3；正式可使用 SSE-S3 或受控的 SSE-KMS。
4. 建议开启 Versioning，用于防范误操作；但不能以 S3 生命周期规则替代 Elasticsearch 的快照删除。
5. 不要对 ES 快照前缀配置对象过期、Glacier、Deep Archive 生命周期。快照之间共享不可变 segment，对象被 S3 自动删除或归档后，快照可能无法恢复。

如果 EC2 位于私有子网，建议在 VPC 中创建 S3 Gateway Endpoint，并把路由表关联到该子网。这样快照流量不经过 NAT Gateway，减少费用和带宽瓶颈。

## 3. AWS IAM：推荐使用 EC2 Instance Profile

推荐给运行 Docker 的 EC2 实例绑定 IAM Role，而不是创建长期 Access Key。`repository-s3` 会通过 EC2 Instance Metadata Service（IMDS）自动取得实例角色凭证，无需把密钥写入 `docker-compose.yml`、环境变量、镜像或日志。

### 3.0 这一步是否需要修改 ES 容器

使用 EC2 IAM Role 时，正常情况下**不需要修改当前 `docker-compose.yml`、不需要向 ES 容器传入 Access Key、也不需要重建 ES 容器**。当前测试 ES 使用官方 `8.19.16` 镜像，S3 repository 可直接使用。

需要完成的是 AWS 控制台侧配置：

```text
S3 Bucket（保存快照）
        +
IAM Role（授权）
        +
EC2 Instance（绑定 Role）
        +
现有 Docker ES 容器（自动通过 IMDS 取得临时凭证）
```

绑定 Role 后，直接执行本文第 4.2 节的仓库注册和 `_verify` 即可验证。只有以下情况才需要改 ES 配置并重启容器：

1. S3 Bucket 不在 EC2 所在 Region，且 ES 无法自动识别 Region，此时才在 `config/elasticsearch.yml` 增加 `s3.client.default.region`。
2. 不采用 IAM Role，改用 Access Key。此时密钥必须写进 Elasticsearch keystore，并且需要额外设计 keystore 的宿主机持久化方案。
3. 使用自建 MinIO 或其他 S3 兼容存储，需要配置自定义 `endpoint`、证书或协议。

### 3.1 创建私有 S3 Bucket（AWS Console）

进入 AWS Console -> **S3** -> **Buckets** -> **Create bucket**，按以下方式创建测试 Bucket：

1. **AWS Region**：选择 EC2 所在区域。可在 EC2 实例详情页查看 Region，例如 `ap-southeast-1`。
2. **Bucket name**：例如 `sano-es-test-snapshots-账号-区域`。名称必须全局唯一，只能使用小写字母、数字和连字符。
3. **Object Ownership**：保持默认的 `ACLs disabled`。
4. **Block Public Access**：保持四项全部勾选。这里的“私有”是指不允许匿名公网访问，并不妨碍绑定 IAM Role 的 EC2 通过授权访问。
5. **Bucket Versioning**：建议启用。它用于降低误删除对象带来的风险，但不能替代 Snapshot 的保留策略。
6. **Default encryption**：测试选择 `SSE-S3` 即可；正式可根据公司安全要求选择 SSE-S3 或 SSE-KMS。
7. 创建后暂时不要配置对象生命周期删除规则，也不要配置 Public Bucket Policy。

创建 Bucket 本身不涉及 ES、Docker 或 Nginx，不会中断任何服务。

### 3.2 创建 IAM Policy

以下是测试 Bucket 的最小权限示例。将 `sano-es-test-snapshots-账号-区域` 替换为真实 Bucket 名。

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListSnapshotBucket",
      "Effect": "Allow",
      "Action": [
        "s3:ListBucket",
        "s3:GetBucketLocation",
        "s3:ListBucketMultipartUploads",
        "s3:ListBucketVersions"
      ],
      "Resource": "arn:aws:s3:::sano-es-test-snapshots-账号-区域"
    },
    {
      "Sid": "ManageSnapshotObjects",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::sano-es-test-snapshots-账号-区域/*"
    }
  ]
}
```

正式环境创建相同结构的 Policy，只替换为正式 Bucket。若同一台 EC2 同时部署测试与正式 ES，实例 Role 需要同时拥有两个 Bucket 的权限；更推荐使用两个独立 Bucket，而不是以共享前缀隔离。

### 3.3 创建并绑定 Role 到 EC2

在 AWS Console：

1. IAM -> Roles -> Create role -> 选择 `AWS service` / `EC2`。
2. 绑定上一步创建的 S3 Policy，Role 名可使用 `sano-es-snapshot-role`。
3. 创建完成后进入 EC2 -> Instances -> 选中运行 ES 的实例。
4. Actions -> Security -> **Modify IAM role**。
5. 选择 `sano-es-snapshot-role` 并保存。

无需重启 EC2 或 Docker 容器。实例角色的临时凭证会自动轮换。

在 EC2 实例详情页的 **Security** 页签可看到 `IAM role`。如果当前显示 `-` 或空值，说明实例尚未绑定实例角色。

### 3.4 检查 HTTPS 与网络访问

S3 Snapshot 不需要开放任何入站端口：

| 通信方向 | 协议和端口 | 是否需要 |
| --- | --- | --- |
| Internet / 内网 -> ES | 无新增要求 | 不因快照改变 |
| EC2 / ES 容器 -> S3 | 出站 HTTPS `TCP 443` | 必须 |
| S3 -> EC2 / ES 容器 | 无 | 不需要开放入站端口 |

ES 会通过 HTTPS 调用 AWS S3 API，AWS 官方 S3 证书链由 JDK 默认信任，不需要在容器中配置证书。S3 Bucket 保持私有即可，访问权限由 IAM Role 决定。

网络按实际子网判断：

1. **EC2 在公有子网，且安全组允许出站 HTTPS**：通常无需额外网络配置，可直接访问 S3。
2. **EC2 在私有子网，有 NAT Gateway/NAT Instance**：允许经 NAT 出站 HTTPS 即可访问 S3，但快照大时可能消耗 NAT 带宽和流量费用。
3. **EC2 在私有子网，没有 NAT**：必须创建 **S3 Gateway VPC Endpoint** 并关联该 EC2 子网对应的 Route Table。Gateway Endpoint 不收费，S3 流量走 AWS 内网，推荐作为正式方案。

#### 在 AWS Console 判断当前实例属于哪一种

不要根据私网地址（例如 `172.31.38.87`）判断。AWS 的公有/私有子网由 **Route Table 路由** 决定。

1. EC2 Console -> Instances -> 选中 ES 所在实例。
2. 在 **Networking** 页签记录 `Subnet ID` 与 `VPC ID`，同时查看是否存在 `Public IPv4 address` 或 Elastic IP。
3. 点击 `Subnet ID` 进入 VPC Subnets 页面。
4. 打开该 Subnet 的 **Route table** 页签，点击关联的 Route Table，再查看 **Routes**。
5. 按下表判断：

| Route Table 中的路由 | 当前网络类型 | S3 Snapshot 处理方式 |
| --- | --- | --- |
| `0.0.0.0/0 -> igw-...`，并且实例有 Public IPv4 / EIP | 公有子网 | 安全组允许出站 TCP 443 即可 |
| `0.0.0.0/0 -> nat-...` | 私有子网，具备 NAT Gateway | 可用；建议后续增加 S3 Gateway Endpoint 降低 NAT 流量 |
| `0.0.0.0/0 -> eni-...` 或 NAT Instance 的实例网卡 | 私有子网，具备 NAT Instance | 可用；同样建议增加 S3 Gateway Endpoint |
| 只有 `local` 路由，或没有可到互联网的 `0.0.0.0/0` 路由 | 私有子网，无 NAT | 必须创建 S3 Gateway Endpoint |
| 看到 `pl-... -> vpce-...`，其中 Prefix List 为 S3 | 已配置 S3 Gateway Endpoint | S3 Snapshot 可走 AWS 内网，不依赖 NAT |

如果 Route Table 同时包含 `0.0.0.0/0 -> nat-...` 和 `pl-... -> vpce-...`，访问同 Region S3 时会优先使用更具体的 S3 Prefix List 路由，即 Gateway Endpoint。

再进入 EC2 实例绑定的 Security Group -> **Outbound rules** 检查：默认的 `All traffic -> 0.0.0.0/0` 已满足要求；若出站规则被收紧，则至少允许 `HTTPS / TCP 443` 到 `0.0.0.0/0`，或在已使用 Gateway Endpoint 时允许到 AWS 管理的 S3 Prefix List。

可在服务器上做一次纯网络连通性检查。将 Region 替换为实际 Region：

```bash
curl -sS -o /dev/null -w 'S3 HTTPS status=%{http_code}\n' --connect-timeout 5 \
  https://s3.ap-southeast-1.amazonaws.com
```

返回 `200`、`301`、`307`、`403` 都说明 DNS 和 HTTPS 网络链路已通；`403` 在未携带 S3 权限签名时是正常结果。该命令不能验证 IAM 权限，最终仍以本文第 4.2 节的 Repository `_verify` 为准。

创建 Gateway Endpoint：VPC Console -> Endpoints -> Create endpoint -> 服务选择 `com.amazonaws.<region>.s3`（类型选择 Gateway）-> 选择当前 VPC -> 勾选 ES 所在子网使用的 Route Table -> Create endpoint。创建后 AWS 自动向该路由表添加 S3 Prefix List 路由。

### 3.5 Docker 使用实例角色时的 IMDS 检查

由于 Elasticsearch 运行在 Docker 容器中，容器需要通过 EC2 的 IMDS 获取 Role 临时凭证。请在 EC2 Console -> Instances -> 选中实例 -> Actions -> Security -> **Modify instance metadata options** 检查：

| 选项 | 建议值 |
| --- | --- |
| Metadata accessible | Enabled |
| Metadata version | V2 only（推荐）或 V1 and V2 |
| Metadata response hop limit | `2` |

`hop limit` 若为 `1`，IMDSv2 返回容器时可能因 Docker 网络多一跳而失败，导致 ES 无法取得 IAM Role 凭证。调整为 `2` 是 AWS 对容器环境的建议；此项是 EC2 配置，不需要重建 Docker 容器。

### 3.6 可选：在宿主机验证实例角色

若主机安装了 AWS CLI：

```bash
aws sts get-caller-identity
aws s3 ls s3://sano-es-test-snapshots-账号-区域/
```

第一条应返回当前 AWS Account 和 IAM Role 身份；第二条可列出 Bucket 内容或返回空列表。若没有安装 AWS CLI，可跳过，后续 Repository Verify 同样能验证 ES 到 S3 的实际权限。

## 4. 测试环境：注册 S3 快照仓库

### 4.1 预检查 ES 状态

在运行 `elasticsearch8-test` 的服务器执行：

```bash
curl -sS 'http://127.0.0.1:9211/_cluster/health?pretty'
curl -sS 'http://127.0.0.1:9211/_cat/indices?v&s=index'
curl -sS 'http://127.0.0.1:9211/_nodes/plugins?filter_path=nodes.*.plugins.name&pretty'
```

要求：

- 集群可访问；单节点测试集群出现 `yellow` 通常是副本分片未分配，可继续测试。
- 不要求额外安装 `repository-s3`。ES 8.19 的 S3 repository 已随发行版提供；若注册时报 `repository type [s3] does not exist`，先确认容器版本和镜像来源是否正确，再排查镜像定制过程。

### 4.2 注册测试仓库

以下命令使用 EC2 IAM Role，不包含 Access Key 或 Secret Key。将 Region、Bucket、Repository 名替换为实际值：

```bash
curl -sS -X PUT 'http://127.0.0.1:9211/_snapshot/sano_s3_test?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "s3",
    "settings": {
      "bucket": "sano-es-test-snapshots-账号-区域",
      "base_path": "elasticsearch8-test",
      "client": "default",
      "server_side_encryption": true,
      "compress": true,
      "max_snapshot_bytes_per_sec": "40mb"
    }
  }'
```

说明：

- `base_path` 不要以 `/` 开头或结尾。
- `server_side_encryption: true` 请求 S3 SSE-S3（AES256）。若 Bucket 默认使用 SSE-KMS，也可由 Bucket 策略处理；此时实例 Role 还需要相应 KMS Key 的 `Encrypt`、`Decrypt`、`GenerateDataKey` 权限。
- `40mb` 是 Elasticsearch 默认的每节点快照限速，测试阶段可显式保留。不要一开始无限速，避免影响同机生产 ES、业务网络或 NAT 带宽。
- API 默认会验证仓库；注册成功说明 ES 已经具备访问 S3 的能力。

验证仓库：

```bash
curl -sS -X POST 'http://127.0.0.1:9211/_snapshot/sano_s3_test/_verify?pretty'
curl -sS 'http://127.0.0.1:9211/_snapshot/sano_s3_test?pretty'
```

如果失败，优先检查：EC2 IAM Role、Bucket Region、S3 Bucket Policy、私有子网的 NAT/VPC Endpoint、服务器 DNS 和出站 HTTPS（443）。

## 5. 测试环境：创建与检查快照

### 5.1 选择演练索引

先列出索引：

```bash
curl -sS 'http://127.0.0.1:9211/_cat/indices?v&s=index'
```

建议第一次只备份一个小索引，例如 `sano_wallet_coin_record_20260703`。快照名使用小写、数字、`-`、`_`，并带时间戳：

```bash
SNAPSHOT_NAME='test-coin-20260715-001'
```

### 5.2 创建单索引快照

```bash
curl -sS -X PUT "http://127.0.0.1:9211/_snapshot/sano_s3_test/${SNAPSHOT_NAME}?wait_for_completion=true&pretty" \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "sano_wallet_coin_record_20260703",
    "ignore_unavailable": false,
    "include_global_state": false
  }'
```

第一次演练使用 `wait_for_completion=true` 便于直接看到结果。生产大快照不要长时间占用 SSH 会话，改用异步创建并查询状态。

### 5.3 异步快照与进度查询

```bash
curl -sS -X PUT 'http://127.0.0.1:9211/_snapshot/sano_s3_test/test-all-20260715-001?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "sano_*,.kibana*",
    "ignore_unavailable": true,
    "include_global_state": false
  }'

curl -sS 'http://127.0.0.1:9211/_snapshot/sano_s3_test/test-all-20260715-001?pretty'
curl -sS 'http://127.0.0.1:9211/_snapshot/_status?pretty'
```

快照状态为 `SUCCESS` 才可作为有效恢复点。`PARTIAL` 表示部分主分片不可用，应检查分片健康后重新创建快照。

### 5.4 查看仓库中所有快照

```bash
curl -sS 'http://127.0.0.1:9211/_cat/snapshots/sano_s3_test?v&s=start_time'
curl -sS 'http://127.0.0.1:9211/_snapshot/sano_s3_test/_all?pretty'
```

快照采用增量存储：后续快照会复用已经上传的不可变 Lucene segment。删除一个快照只删除不再被其他快照引用的对象，因此必须通过 Elasticsearch API 删除。

## 6. 测试环境：恢复演练

恢复有两种安全方式：

1. **推荐演练方式：重命名恢复。** 不影响原索引，可直接对比恢复结果。
2. **灾难恢复方式：删除/关闭旧索引后原名恢复。** 只在确认需要覆盖数据时使用。

### 6.1 重命名恢复（推荐）

先确认快照内容：

```bash
curl -sS 'http://127.0.0.1:9211/_snapshot/sano_s3_test/test-coin-20260715-001?pretty'
```

将索引恢复为 `restore_check_*`，不恢复全局状态：

```bash
curl -sS -X POST 'http://127.0.0.1:9211/_snapshot/sano_s3_test/test-coin-20260715-001/_restore?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "sano_wallet_coin_record_20260703",
    "ignore_unavailable": false,
    "include_global_state": false,
    "rename_pattern": "(.+)",
    "rename_replacement": "restore_check_$1"
  }'
```

监控恢复：

```bash
curl -sS 'http://127.0.0.1:9211/_cluster/health?wait_for_status=yellow&timeout=10m&pretty'
curl -sS 'http://127.0.0.1:9211/_cat/recovery/restore_check_sano_wallet_coin_record_20260703?v'
curl -sS 'http://127.0.0.1:9211/_cat/indices/restore_check_sano_wallet_coin_record_20260703?v'
```

对比文档数：

```bash
curl -sS 'http://127.0.0.1:9211/sano_wallet_coin_record_20260703/_count?pretty'
curl -sS 'http://127.0.0.1:9211/restore_check_sano_wallet_coin_record_20260703/_count?pretty'
```

文档数一致后，再抽查典型 `id`、Mapping、聚合查询结果。恢复验证完成后删除演练索引：

```bash
curl -sS -X DELETE 'http://127.0.0.1:9211/restore_check_sano_wallet_coin_record_20260703?pretty'
```

### 6.2 覆盖式原名恢复（仅灾难恢复）

Elasticsearch 不能直接向一个已打开的同名索引恢复。必须先停止写入，删除原索引或关闭同名索引；删除方式最简单但不可逆，因此先确认存在可用快照。

```bash
# 1. 停止 es-server 导入和写入来源，确认快照状态为 SUCCESS。
# 2. 可选：先创建当前状态的保护快照。
# 3. 删除目标索引。此命令不可逆，执行前二次确认名称。
curl -sS -X DELETE 'http://127.0.0.1:9211/sano_wallet_coin_record_20260703?pretty'

# 4. 以原名恢复。
curl -sS -X POST 'http://127.0.0.1:9211/_snapshot/sano_s3_test/test-coin-20260715-001/_restore?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "sano_wallet_coin_record_20260703",
    "include_global_state": false
  }'
```

恢复后执行 6.1 的健康、recovery、count 校验，再恢复 `es-server` 写入。

## 7. 正式环境执行流程

测试闭环通过后，正式环境按以下顺序执行：

1. 创建独立正式 Bucket 和正式 IAM Policy，绑定到正式 ES 所在 EC2 的 Instance Role。
2. 确认正式 ES 能访问 S3：注册 `sano_s3_prod` 并执行 `_verify`。
3. 第一次手工创建全量快照，确认 `SUCCESS`，并在测试环境用“重命名恢复”验证一个索引。
4. 确认恢复结果后，再配置每日自动快照和保留策略。

正式仓库注册示例：

```bash
curl -sS -X PUT 'http://127.0.0.1:9201/_snapshot/sano_s3_prod?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "s3",
    "settings": {
      "bucket": "sano-es-prod-snapshots-账号-区域",
      "base_path": "elasticsearch8-prod",
      "client": "default",
      "server_side_encryption": true,
      "compress": true,
      "max_snapshot_bytes_per_sec": "40mb"
    }
  }'
```

注意：正式环境实际 HTTP 端口以 `elasticsearch8/docker-compose-elasticsearch.yml` 为准。不要照抄示例中的 `9201` 后直接执行。

### 7.1 正式全量快照建议

当前业务索引以 `sano_*` 为主，首次建议先备份业务索引与任务索引，不恢复全局集群配置：

```bash
curl -sS -X PUT 'http://127.0.0.1:9201/_snapshot/sano_s3_prod/prod-all-20260715-001?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "sano_*",
    "ignore_unavailable": false,
    "include_global_state": false
  }'
```

`include_global_state: false` 可避免恢复时覆盖目标集群的 persistent settings、模板、pipeline、ILM 等全局配置。当前主要目标是业务索引数据恢复，默认不建议恢复全局状态。

## 8. 配置每日自动快照（SLM）

首次手工验证成功后，可在正式集群创建每日凌晨 03:30 的策略，保留最近 14 个成功快照。快照命名中的 `<{now/d}>` 会在执行时被替换为日期。

```bash
curl -sS -X PUT 'http://127.0.0.1:9201/_slm/policy/sano_daily_snapshot?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "schedule": "0 30 3 * * ?",
    "name": "sano-daily-<{now/d}>",
    "repository": "sano_s3_prod",
    "config": {
      "indices": ["sano_*"],
      "ignore_unavailable": false,
      "include_global_state": false
    },
    "retention": {
      "expire_after": "14d",
      "min_count": 7,
      "max_count": 14
    }
  }'
```

检查与手动触发：

```bash
curl -sS 'http://127.0.0.1:9201/_slm/policy/sano_daily_snapshot?pretty'
curl -sS -X POST 'http://127.0.0.1:9201/_slm/policy/sano_daily_snapshot/_execute?pretty'
curl -sS 'http://127.0.0.1:9201/_slm/status?pretty'
curl -sS 'http://127.0.0.1:9201/_slm/stats?pretty'
```

保留清理由 Elasticsearch 执行。不要同时为同一 S3 前缀建立 S3 对象过期策略。

## 9. 跨集群恢复到测试环境

若要把正式快照恢复到测试集群做验证，测试集群注册正式仓库时必须只读：

```bash
curl -sS -X PUT 'http://127.0.0.1:9211/_snapshot/sano_s3_prod_readonly?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "type": "s3",
    "settings": {
      "bucket": "sano-es-prod-snapshots-账号-区域",
      "base_path": "elasticsearch8-prod",
      "client": "default",
      "readonly": true
    }
  }'
```

随后列出正式快照并以重命名方式恢复：

```bash
curl -sS 'http://127.0.0.1:9211/_cat/snapshots/sano_s3_prod_readonly?v&s=start_time'

curl -sS -X POST 'http://127.0.0.1:9211/_snapshot/sano_s3_prod_readonly/prod-all-20260715-001/_restore?pretty' \
  -H 'Content-Type: application/json' \
  -d '{
    "indices": "sano_wallet_coin_record_20260703",
    "include_global_state": false,
    "rename_pattern": "(.+)",
    "rename_replacement": "from_prod_$1"
  }'
```

绝不能让测试、正式两个集群以可写方式注册同一个 Bucket + `base_path`。

## 10. 常见问题排查

### 10.1 `repository type [s3] does not exist`

确认容器实际镜像版本：

```bash
docker inspect elasticsearch8-test --format '{{.Config.Image}}'
curl -sS 'http://127.0.0.1:9211/'
```

应为官方 Elasticsearch `8.19.16`。不要把 S3 依赖当作应用侧插件安装到 `es-server`；仓库由 Elasticsearch 节点自身访问。

### 10.2 `AccessDenied`、`Unable to find a region` 或仓库验证失败

依次检查：

1. EC2 是否已绑定包含 S3 权限的 IAM Role。
2. Bucket 名、Region、Bucket Policy 是否正确。
3. EC2 是否能出站访问 S3 的 `443` 端口；私有子网建议检查 NAT 或 S3 VPC Endpoint。
4. 若 Bucket 不在默认 Region，可在仓库注册前将以下非敏感设置加入 `config/elasticsearch.yml` 并重启容器：

```yaml
s3.client.default.region: ap-southeast-1
```

5. 不要把 `access_key`、`secret_key` 写入 `elasticsearch.yml` 或 Compose。若无法使用 EC2 IAM Role，必须通过 Elasticsearch keystore 保存，并确保 keystore 在容器重建后持久化；该方案需要单独设计后再使用。

### 10.3 快照长期 `IN_PROGRESS`

```bash
curl -sS 'http://127.0.0.1:9211/_snapshot/_status?pretty'
curl -sS 'http://127.0.0.1:9211/_cat/shards?v'
curl -sS 'http://127.0.0.1:9211/_cluster/allocation/explain?pretty'
```

检查主分片是否可用、S3 网络是否抖动、快照限速是否过低。不要直接删除 S3 内正在使用的对象。

### 10.4 快照为 `PARTIAL`

`PARTIAL` 通常说明某些主分片不可用。记录失败分片，恢复集群健康后重新创建快照；不要把 `PARTIAL` 当作完整灾备快照。

### 10.5 恢复时报索引已存在

优先使用“重命名恢复”。若必须原名恢复，先停止写入并删除或关闭同名索引；关闭恢复要求主分片数匹配，删除再恢复的流程更直接，但必须确认快照可用。

## 11. 日常运维检查清单

每次重要版本升级、Mapping 重大调整或批量导入前后：

1. `GET _cluster/health` 确认主分片正常。
2. 创建一个手工快照，确认状态 `SUCCESS`。
3. 至少每月在测试环境执行一次重命名恢复与 count/查询校验。
4. 检查 SLM 最近执行时间、失败次数、保留数量。
5. 检查 S3 Bucket 的对象数量、存储费用、Versioning 的非当前版本费用。

快照是数据恢复的最后一道保险；只有完成过实际恢复验证的快照，才算真正可用的备份。
